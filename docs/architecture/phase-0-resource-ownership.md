# Phase 0 resource ownership manifest

- Status: complete characterization baseline with later route-switch resolutions called out explicitly.
- Date: 2026-08-10
- Scope: every Windows mutation reachable from automatic features, Adaptive Engine, Process List/manual actions, persistent settings commands, and crash recovery.

This is the behavioral inventory required before a mechanism can move behind a typed controller.
Unresolved rows preserve the Phase 0 implementation; completed route switches are called out in
their rows and linked completion evidence. The manifest does **not** approve unrecorded changes to
precedence, storage, recovery, or user-visible behavior.

## Rules used by this manifest

`temporary` means Winderust must preserve the pre-Winderust value and release it. `process-lifetime` means the OS request belongs to this Winderust process and must be explicitly released on normal shutdown, but it is not represented as a process-state baseline. `persistent` means an explicit user command changes Windows configuration beyond the running process. `irreversible` means Winderust must not pretend a restoration exists.

For every temporary external-process, thread, suspension, or automatic power-plan mutation, the existing safety barrier is: read the baseline from the validated identity, send a `Begin` intent to the helper and wait, apply the setter, then commit. The journal carries original and expected values, compacts successive compatible segments, and only unwinds an entry while the live value still equals the expected value ([crash_recovery.rs](../../src/backend/crash_recovery.rs#L373), [crash_recovery.rs](../../src/backend/crash_recovery.rs#L555)). Process identity includes PID, creation time, and image path; manual actions also revalidate the selected target before applying ([process_list.rs](../../src/foreground/process_list.rs#L300)).

The helper has four recovery entry variants: process property, thread priority, active power plan, and a suspended Job Object ([crash_recovery.rs](../../src/backend/crash_recovery.rs#L373), [crash_recovery.rs](../../src/backend/crash_recovery.rs#L391), [crash_recovery.rs](../../src/backend/crash_recovery.rs#L409), [crash_recovery.rs](../../src/backend/crash_recovery.rs#L430)). It retries journal recovery and stale Adaptive-plan cleanup three times after an unclean main-process exit ([crash_recovery.rs](../../src/backend/crash_recovery.rs#L315)). Timer resolution, Winderust self-power, persistent configuration, and irreversible commands deliberately are not process-value journal entries.

## Lifecycle and precedence facts to preserve

1. The normal hidden-loop apply order is Background Efficiency, Workload Engine, I/O, Process Priority, Thread Priority, Dynamic Priority Boost, GPU Priority, Memory Priority, result-bearing manual commands, App Suspension, CPU Sets (Soft), Processor Affinity (Hard), Core Limiter, By Running App, automatic Memory Trim, then Timer Resolution. This order is observable whenever two producers touch the same property.
2. Shutdown deliberately runs in reverse ownership/application order: Timer Resolution through Background Efficiency, then Adaptive-plan and original automatic-plan release ([runner.rs](../../src/backend/automation/runner.rs#L102)). A controller cutover must preserve that effective reverse release, not rely on field destruction.
3. Phase 6 resolves CPU allocation overlap in one coordinator: CPU Sets (Soft) > Processor Affinity (Hard) > Core Limiter > Adaptive Engine. Shadowed claims remain policy desires, CPU Sets and affinity are mutually exclusive live properties, and `RuntimeCore` reconciles affected exact keys once after the whole CPU-control phase rather than applying a lower claim inside a releasing feature or during shutdown ([phase-6-cpu-allocation.md](phase-6-cpu-allocation.md)).
4. Adaptive Engine replaces static settings for Thread/I/O/GPU/Dynamic Priority Boost through `effective_*_settings`; do not recast this as a last-writer accident. Memory Priority is the exception: it is currently last writer after Workload Engine and requires an explicit approval before normalizing.
5. Process List one-shot actions are not claims. They use the same raw mutation helpers (and therefore helper journaling) but retain a separate UI restoration closure. Later automatic work may replace their values. A complete property cutover must move these producers with the automatic producers, then remove—not wrap—the UI stack.

## Source-search gates

Run `scripts/check_architecture_ownership.ps1` after every mechanism cutover. It is the executable source of truth for the gates below and fails on any direct raw setter or import outside the listed current boundary. The allowlists describe the **current** characterization; replace an allowlist only as part of the same complete mechanism route switch. Do not use a broad `src/features` or `src/ui` allowlist.

The gate covers process priority and throttling, thread priority, Dynamic Priority Boost, I/O and GPU priority, CPU Sets (Soft), Processor Affinity (Hard), App Suspension Job Objects, Timer Resolution, Memory Trim, process termination, power-plan writes, Win32 Priority Separation registry writes, and startup registration. `rg` matches imports as well as invocations; that is intentional because an unapproved raw-setter import is an architectural boundary breach.
